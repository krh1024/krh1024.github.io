# 기술 스택 및 코딩 규칙

## 기술 스택

| 영역 | 기술 |
|------|------|
| 프레임워크 | Vue 3 (Options API 패턴) |
| 상태 관리 | Pinia |
| HTTP 통신 | axios |
| 데이터베이스 | MariaDB 10 |
| 라우팅 | vue-router (기존 Ziggy `route()` 패턴 우선) |

## Vue 컴포넌트 작성 규칙

- **Options API 패턴**을 따른다. Composition API (`<script setup>`) 전환은 사용자가 별도로 요청한 경우에만 수행한다.
- 파일 작성 순서는 항상 **템플릿 → 스크립트 → 스타일시트** 순으로 유지한다.
- 생명주기 훅(mounted, created, beforeDestroy 등)을 우선시하여 개발한다.

## 상태 관리

- 전역 상태는 **Pinia** 스토어로 관리한다.
- jQuery, React, `fetch` 기반 구현은 사용자의 별도 요청 없이 도입하지 않는다.

## HTTP 통신

- 백엔드와 통신할 때는 **axios** 만 사용한다.
- API Resource는 기존 **camelCase 응답 필드** 및 문자열 `trim()` 처리 관례를 따른다.

## 데이터베이스

- **MariaDB 10** 을 사용하며 기존 테이블 구조를 유지한다.
- 마이그레이션 파일을 생성하거나 기존 스키마를 변경하지 않는다.
- 테이블, 컬럼, 자료형 및 관계를 추측하지 않는다. 필요 시 읽기 전용 조회를 사용자에게 허가받아 실제 구조를 확인한다.

## 코드 스타일

- **4칸 들여쓰기** 및 **LF 줄바꿈** 관례를 따른다.
- 린트·포맷 명령어:
  - `npm run lint` — oxlint + ESLint 순서로 실행 (`.oxlintrc.json`, `eslint.config.js` 기준)
  - `npm run format` — Prettier (`src/` 대상, `.prettierrc.json` 기준)

## 라우팅

- 신규 블로그에서 기존 블로그 라우트를 참조할 때는 기존 **Ziggy `route()`** 사용 패턴을 우선한다.

## UI 및 접근성

- UI 변경 시 기존 컴포넌트를 재사용한다.
- 접근성(ARIA), 모바일 화면, 관리자·고객 화면의 기존 스타일을 함께 고려한다.

## 다국어(i18n)

- 다국어 기능 변경 시 **한국어·영어** 리소스와 언어별 뷰(view)에 미치는 영향을 함께 확인한다.

## 테스트 및 검증

- 코드 변경 후 변경 범위에 맞는 문법 검사, 코드 스타일 검사, 관련 테스트 및 회귀 영향 확인을 제안한다.
- 검사나 테스트 명령 실행 전에 명령어, 실행 이유, 대상 범위, 예상 결과 및 발생 가능한 영향을 설명하고 사용자의 허가를 받는다.
- 테스트는 정상 처리, 유효성 실패, 권한 실패, 존재하지 않는 데이터, 경계값 및 예외 상황을 검증한다.
- 테스트 간 의존성을 만들지 않으며, 구현 세부사항보다 외부에서 관찰 가능한 동작과 회귀 방지를 우선 검증한다.
- 검증이 실패하면 실패 사실을 숨기지 않고 원인, 영향, 미수행 검증 및 남은 위험을 사용자에게 보고한다.
