# API, 예외 처리 및 보안

## API 사용 관례

- 기존 내부 API의 사용 관례를 유지한다.
- 신규 엔드포인트 추가 시 인증·인가·CSRF 적용 범위를 반드시 확인한다.
- 인증이 필요한 관리자 API에는 기존 권한 검사를 유지한다.

## 예외 처리 체계

| 오류 유형 | 사용 예외 클래스 |
|-----------|----------------|
| 웹 페이지 오류 | `PageException` |
| API 오류 | `ApiException` |

- 기존 예외 처리 체계를 벗어나는 패턴을 임의로 도입하지 않는다.

## 보안 원칙

### 시크릿 및 개인정보 보호

- `.env` 값, API 키, 토큰, SecretKey, 암호화 키 및 개인정보를 사용자 응답, 명령 출력, 로그 또는 코드 주석에 **절대 노출하지 않는다**.

### 로그

- 로그가 필요한 경우 개인정보를 최소화한다.
- 전화번호 등 식별 정보는 기존 정책과 작업별 Spec에 따라 **마스킹** 처리한다.

### SQL 보안

- Raw Query가 필요한 경우 문자열 결합을 피하고 **파라미터 바인딩**을 우선한다.
- SQL Injection 가능성을 반드시 검토한다.

## 코드 리뷰 우선순위

코드 리뷰는 아래 순서로 확인한다.

1. 기능적 오류
2. 기존 기능 회귀
3. 보안
4. 데이터 정합성
5. 데이터베이스 쿼리
6. 성능
7. 예외 처리
8. 유지보수성
9. 코드 스타일

## 리뷰 지적 원칙

- 지적에는 대상 파일과 위치, 원인, 실제 영향, 재현 또는 판단 근거 및 개선 방법을 포함한다.
- 근거 없는 문제나 개인 취향만을 이유로 변경을 요구하지 않는다.
- 문제가 확인되지 않으면 억지로 지적 사항을 만들지 않는다.

## 작업 완료 보고

작업 완료 시 다음 항목을 사용자에게 보고한다.

- 변경된 파일 목록
- 주요 변경 내용
- 영향 범위
- 수행한 검증과 결과
- 남아 있는 위험이나 미검증 사항
