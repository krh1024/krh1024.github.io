# 프로젝트 개요 및 작업 원칙

## 프로젝트 개요

이 프로젝트는 기존 블로그(`D:\pi\ras-blog`)에서 신규 블로그(`D:\blog`)로 기술을 이전하는 마이그레이션 프로젝트입니다.

## 작업 권한 원칙

- 프로젝트 내부의 소스코드, 설정 파일, 문서 및 그 밖의 모든 파일은 사용자의 사전 허가 없이 **읽기 전용**으로 조회할 수 있다.
- 파일의 생성, 수정, 이동 및 삭제는 이 문서에서 별도로 정한 예외를 제외하고 **사용자의 사전 허가**가 필요하다.
- 데이터베이스에는 사용자의 사전 허가 없이 접속할 수 없다.
- 데이터베이스 작업은 원칙적으로 **읽기 전용 조회**만 허용한다.

## 허가 요청 시 설명 의무

사용자에게 허가를 요청할 때에는 다음 내용을 자세하고 명확하게 설명한다.

- 작업을 수행하려는 이유
- 사용할 정확한 명령어 또는 수행할 조작
- 해당 명령어나 조작이 영향을 미치는 대상과 범위
- 실행 결과로 예상되는 변경 사항 및 부작용 가능성

## 코드 수정 시 사전 고지

코드를 수정하기 전에 반드시 사용자에게 아래 내용을 설명하고 명시적인 허가를 받아야 한다.

- 수정 대상 파일의 경로
- 수정할 행 번호 또는 행 범위 (확정 불가 시 대상 함수·클래스·코드 블록의 정확한 위치)
- 코드를 어떻게 변경할 것인지
- 해당 변경이 필요한 이유

## 사용자와의 소통

- 작업의 근거, 영향 및 결과를 최대한 자세하게 설명한다.
- 내부 추론 과정은 노출하지 않는다. 결론, 근거, 확인 결과 및 위험 요소를 명확하게 제공한다.

## 코드 주석 작성 규칙

변경 이력이나 변경 사유 주석이 필요한 경우 다음 형식을 사용한다.

```text
/**
 * YYYY-MM-DD by codex (User: 사용자명) - 변경 내용
 * 변경 이유, 관련 데이터, 예외 사항 또는 판단 근거
 */
```

- 날짜는 주석 작성 당일을 기준으로 `YYYY-MM-DD` 형식으로 기록한다.
- 작성자 표기는 `codex`로 고정한다.
- `User`에는 해당 변경을 요청하거나 승인한 사용자의 이름을 기록한다. 이름이 불명확하면 사용자에게 확인한다.
- 사용하는 언어가 블록 주석 문법을 지원하지 않으면 같은 문구 규격을 유지하면서 해당 언어에 맞는 주석 문법을 사용한다.

## 지침 우선순위

`사용자의 최신 명시적 지시` → `AGENTS.md` 순으로 우선 적용한다.

## 작업 전 분석 및 변경 원칙

- 작업 시작 전 요청과 관련한 기존의 유사한 구현을 확인한다.
- 데이터베이스의 테이블, 컬럼, 자료형 및 관계를 추측하지 않는다. 확인이 필요하면 읽기 전용 조회를 사용자에게 승인받고 실제 구조를 확인한다.
- 기존 컴포넌트 및 공통 스크립트 등 재사용 가능한 구현을 우선 확인한다.
- 사용자가 요청하지 않은 리팩터링, 기능 추가, 파일 정리 및 동작 변경을 수행하지 않는다.
- 요청을 충족하는 범위에서 변경 파일과 코드 변경량을 최소화하고 기존 동작을 최대한 보존한다.
- 기존 기능의 동작이나 외부 연동 계약이 달라질 가능성이 있으면 수정 전에 영향과 위험을 사용자에게 알린다.
